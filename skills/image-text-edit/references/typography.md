# 字体匹配中容易误判的细节

## 字体名称只是起点

确认来源平台、文字语言、截图比例及可用字体。Apple 官方将 SF Pro 列为 iOS/iPadOS/macOS 的系统字体，但这不能证明任意应用的任意标签都使用同一字重或字号。

- [Apple Fonts](https://developer.apple.com/fonts/)
- [Apple Design Resources](https://developer.apple.com/design/resources/)
- [Apple Typography Guidelines](https://developer.apple.com/design/human-interface-guidelines/typography)
- [Apple 工程师关于 iOS 中文 UI 字体变化的说明](https://developer.apple.com/forums/thread/758189)

系统、应用及字体版本影响结果。对版本相关事实需要时重新查询。SF 拉丁字与中文可能来自不同字体；不能将中文一律硬编码为某个 PingFang 文件。使用系统字体 API 时检查实际 glyph runs，确认是否发生字体回退。私有字体名未必能直接加载；指定字体失败时不能默默改成 Times 或其他字体。

## 在逻辑字号下排版，再按截图比例渲染

截图里的 34 像素文字可能来自 17 pt × 2，也可能来自别的组合。直接以 34 pt 排版会改变字体的光学尺寸与动态字距，即使字高看似相同也不一定匹配。

对已知 @2x Apple 界面，可用 CoreText 在 17 pt 等逻辑字号下排版，再将绘图上下文缩放 2 倍。比例必须由当前截图确认，不能将本案例的数值推广到其他图片。

## 分开处理位置、字重和字距

- 小数像素起点会明显改变边缘灰度。搜索至少包括整数和半像素相位。
- 基线与字框顶部不同。中文、数字的顶部也未必齐平。
- 字重调整不能用来抵消位置偏差。先比较轮廓，再检查边缘灰度。
- 不指定 kern 与显式 kern=0 可能产生不同结果；前者可能启用系统动态 tracking。
- 中英文混排可能引入自动空隙。单独的数字完全匹配，不代表“数字＋年月日”整行匹配。可分段校准，保留原有中文和时间像素，或使用明确定位的多个文本 run。
- 不缩放已经栅格化的文字。移动原有字形时使用整数像素；确需小数位置的新字由排版引擎重新栅格化。

## 衡量匹配

使用未缩放的旧文字裁剪，排除邻近图标及无关文字。记录比较区域和不同像素数，结合最大通道差、平均绝对差和放大对比判断。大片纯色区域会稀释平均差值；必要时使用前景掩码或逐片段比较。

完全匹配的标准是该区域解码后的 RGBA 像素相同。这里不是要求 PNG 压缩字节、文件体积或元数据相同。若校准仅覆盖拉丁字或数字，报告时明确范围；新出现的汉字、数字及标点另做检查。

发现不能完全匹配时，先判断是字形差异、版本、动态字距、颜色、抗锯齿还是坐标相位问题。不要无限增加无依据的参数搜索，也不要将最小误差自动解释为可接受。
